==========================================================================
L3.3 — Tanpa lock: race condition (harapan A=500, B=1000, total=1500)
==========================================================================
dengan lock                     : A= 500 B=1000 total=1500  (0.04s)
tanpa lock                      : A= 500 B=1000 total=1500  (0.04s)
tanpa lock + jendela 2 ms       : A= 850 B= 650 total=1500  (0.06s)
dengan lock + jendela 2 ms      : A= 500 B=1000 total=1500  (0.13s)

Catatan jujur: menghapus lock saja sering TIDAK memunculkan kerusakan
pada CPython (GIL + critical section sangat pendek). Jendela baca->tulis
2 ms memperbesar peluang dan membuktikan bug-nya nyata (lost update).

==========================================================================
Analisis P3 — Server restart: dedup RAM vs dedup SQLite
==========================================================================
dedup=ram   : A=900 -> retry -> A=800 (transfer terjadi 2x)
dedup=sqlite: A=900 -> retry -> A=900 (transfer terjadi 1x)

Kesimpulan: dedup di RAM kehilangan jaminan at-most-once setelah restart.
Perbaikan: saldo + log request_id di SQLite, ditulis dalam SATU transaksi
atomik (BEGIN IMMEDIATE). Yang dicapai: at-least-once + dedup = effectively-once.

Ringkasan angka disimpan: praktikum3/hasil/l3_ringkasan.json
